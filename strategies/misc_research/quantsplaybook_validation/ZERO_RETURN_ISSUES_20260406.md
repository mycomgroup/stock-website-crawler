# 米筐平台零收益策略问题假设与已验证共性总结

## 使用说明

这份文档是“零收益问题假设与已验证共性总结”，不是逐文件审计结论。

- 文中的“已确认问题”表示已经在当前修复过程中被平台回测或源码排查反复验证。
- 文中的“待验证问题”表示高频怀疑模式，适合作为排查方向，但不能直接当作单个策略的最终原因。
- `0.00%` 本身不等于“代码有错”。有些策略是逻辑空跑，有些是回测频率不对，有些是候选集长期为空，也有少数只是当前区间内确实没有触发。

## 已确认问题

### 1. 回测频率错误

这是目前已经确认的高优先级问题之一。

- 很多短线、竞价、打板、盘中止损策略，本质上依赖分钟级回测。
- 如果这些策略被按 `day` 频率提交，平台通常不会报错，但会表现成“正常完成 + 0.00% + 几乎不交易”。
- 这类问题已经在当前修复中实锤过，所以不能再把所有零收益都简单归为策略逻辑错误。

典型策略类型：
- 集合竞价策略
- 首板/二板/连板策略
- 日内交易策略
- 盘中止损/盘中买卖策略

当前已确认需要特别注意的代表：
- `rq_32_追高概率涨停.py`
- `rq_55_怎么让龟速变奔跑以首版突破一进二为例.py`
- `rq_78 首板低开策略-终极版 最大回撤15%，年化50%.py`
- `rq_83_开盘幅度决定日内方向.py`
- `rq_96_集合竞价量比策略V1.py`
- `rq_99_韶华研究之二十_竞价异动.py`

### 2. 调度时间规则不兼容

- 聚宽常见写法是字符串时间或 `run_daily(func, "09:35")` 风格。
- 米筐这里更依赖 `scheduler.run_daily(..., time_rule=market_open(...))` 这一套规则。
- 这不只是语法问题。对分钟策略来说，时间规则写法不兼容时，可能直接导致策略无法在预期时点触发，甚至启动阶段就失败。

已确认现象：
- `market_open(hour=14, minute=0)` 这类写法在当前迁移策略里出现过问题。
- 改成交易分钟偏移后，平台行为更稳定，比如改为 `market_open(minute=180)` 这种形式。

### 3. 因子结果结构与索引层级差异

- 聚宽迁移过来的很多策略默认 `get_factor(...)` 返回结构与原平台一致。
- 在米筐侧，很多地方需要显式处理 `DataFrame`、列名、索引层级，不能直接按原来的 `groupby(level=0)`、字段访问方式照搬。
- 这类问题非常容易造成“候选集为空”或“except 吞掉后静默空跑”。

当前已确认的高频修法：
- 单因子结果先转 `DataFrame`
- 明确检查返回是否为空
- 某些文件需要把 `groupby(level=0)` 改成 `groupby(level=-1)` 再取末值

已确认受影响代表：
- `rq_07_为了积分实盘策略.py`
- `rq_36 最简强者恒强策略.py`
- `rq_61_抄底神器2.0低回撤高成功率.py`
- `rq_85_价值策略重开再次向Jqz1226致敬.py`

### 4. ETF 防守资产被错误处理成空仓

- 一批 ETF 轮动策略原本有债券 ETF/防守 ETF 兜底。
- 迁移后却因为 `scores` 为空、`best_score <= 0`、或过度依赖 `bar_dict/is_trading`，最终变成整月整周空仓。
- 这类问题在平台上通常不会报错，只会表现成 `0.00%`。

当前已确认修复方向：
- 有防守资产时，不要直接 `return` 空仓
- 不要把“没有进攻标的”错误等价成“什么都不持有”
- 某些 ETF 策略里，下单前过度检查 `bar_dict` 反而导致始终不下单，需要直接 `order_target_value(...)`

已确认受影响代表：
- `rq_13_不含未来宽基etf轮动8年50倍年化60.py`
- `rq_46 八仙过海V2.py`
- `rq_73_优化宽基etf追涨.py`
- `rq_76 ETF基金溢价高收益低回测策略 改进版.py`
- `rq_78 【基金增强思考2.0】优秀基金的持续性与周期的关系密不可分.py`
- `rq_82 无需先验知识，动态选择的etf轮动策略，更具鲁棒性.py`
- `rq_85_稳健型ETF策略.py`

### 5. 周期标记写得太早

- 一些周度/月度调仓策略会在函数一开始就把 `week` / `month` 标记写掉。
- 如果这一轮候选为空、过滤失败、或者下单目标为空，后面整周整月就不会再尝试。
- 这种 bug 很隐蔽，因为平台不会报错，只会长期没有交易。

当前已确认修法：
- 只有在“真正选出目标并准备调仓”之后再写周期标记

已确认受影响代表：
- `rq_07_为了积分实盘策略.py`
- `rq_32_追高概率涨停.py`
- `rq_36 最简强者恒强策略.py`
- `rq_61_抄底神器2.0低回撤高成功率.py`

### 6. 候选池筛选过严或方向不对

- 某些策略迁移后虽然能运行，但筛选条件和米筐数据结构不匹配，导致候选永远为空。
- 另一类是“有候选，但没有排序”，最后买入集合不稳定甚至为空。
- 这类问题比平台 API 报错更常见。

已确认现象：
- 市值/PE/成长因子筛选后没有排序，直接 `head(...)`
- 使用了不合理的上下限组合
- 候选集太小，叠加均线/动量/停牌过滤后直接归零

## 待验证问题

下面这些是高频怀疑项，但当前还不能在文档里写成“已确认结论”。

### 1. 涨停价 / 涨停状态获取差异

这个方向是对的，但不能简单说“是最严重问题”。

- 聚宽里大量策略依赖 `get_current_data()[stock].high_limit`
- 米筐里经常要改成 `history_bars(..., 'limit_up')`、`bar.limit_up`、或手动计算
- 真实问题往往不只是“取不到涨停价”，还包括盘中比较逻辑、板块涨跌停制度差异、以及 `bar_dict` 使用位置不对

所以更准确的分类名应该是：
- `涨停价 / 涨停状态获取差异`

### 2. 复杂因子缺失

这个方向仍然重要，但目前不适合写成“40+ 已确认”。

- 一批多因子策略确实依赖更复杂的技术指标、质量因子、动量因子、波动率因子
- 但并不是所有零收益因子策略都卡在这里
- 现在更准确的说法是：这是一个高频排查方向，而不是已经完成的分桶统计

### 3. 实时数据接口差异

这个问题存在，但建议写得更具体一些。

不建议只写：
- 聚宽 `get_current_data()`
- 米筐 `bar_dict`

更准确的写法应该是：
- `bar_dict`
- `bar.close / bar.limit_up / bar.is_trading`
- 不同回调阶段可拿到的数据语义
- 某些策略下单前过度依赖实时对象，反而导致空跑

### 4. 数据结构差异

这个分类本身没错，但当前建议降级到“通用背景问题”。

- 它通常不是最终根因本身
- 更常见的是它衍生出的具体问题：索引层级错、字段访问错、返回值为空没处理、numpy / DataFrame 混用

## 不建议继续保留的旧表述

下面这些说法建议不要再用：

- `涨停价获取问题（最严重）`
- `受影响策略数量：约 60+ 个`
- `复杂因子缺失：约 40+ 个`
- `实时数据差异：约 30+ 个`
- `定时任务差异：影响轻微`

原因：
- 当前没有逐文件核实统计支撑这些数字
- “轻微”这个判断对分钟策略不成立
- 会误导后续优先级

## 建议的修复优先级

### P0

- 回测频率错误
- 调度时间规则不兼容
- 启动即空跑或启动即失败的分钟/竞价策略

### P1

- ETF 防守资产被错误处理成空仓
- 周期标记写太早
- 因子结果结构 / 索引层级错误
- 候选集长期为空

### P2

- 复杂因子缺失，需要手动补算
- 数据结构适配类收尾问题
- 个别模板化转换遗留问题

## 建议保留的修复模板方向

下面这些模板思路仍然是有价值的，可以继续保留：

- 涨停价 / 涨停状态统一工具函数
- 技术指标手动计算函数
- 股票池筛选与候选数检查
- 调仓前日志与候选数量日志

但建议在模板前加一句：
- `以下模板用于加速修复，不代表所有零收益策略的根因都相同。`

## 当前结论

这批零收益策略不能再按“单一平台 API 差异”来理解。

更准确的结论是：
- 一部分是分钟/日频配置错误
- 一部分是 ETF 轮动逻辑把防守仓错误变成空仓
- 一部分是因子结果结构与索引层级不匹配
- 一部分是周/月标记写太早
- 还有一部分才是复杂因子缺失或技术指标未实现

所以，这份文档最适合用作：
- 修复方向说明
- 排查优先级说明

而不适合直接当作：
- 逐文件准确根因统计报告
