## 核心原则

### 1. 当前策略是主仓 alpha 原型

当前 `strategy.py` 的核心收益来源默认已经存在。

你要做的是：

- 修复工程缺口
- 微调 alpha 参数
- 补主路由和总暴露控制
- 增加轻量过滤与确认
- 强化执行、权重、退出与再进场

你**不要**做的是：

- 把原有 alpha 推翻重写
- 用新机制替代原有核心选股逻辑
- 把一个增强模块强行升格成新的主策略

### 2. 先修结构，再调参数

如果策略里存在明显的工程问题，那么继续调参数是低效甚至误导的。

例如：

- 声明了状态变量，但从未写入或清理
- 主路由名义上控制仓位，实际上只在风格间切权重
- 时间止损、再进场、涨停打开卖出等规则没有真正接通
- 目标持仓没有去重、没有目标权重表、没有现金缓冲
- 持仓记录、成本记录、入场日期记录彼此不一致

### 3. 分层搜索，不混搜

每次只允许改**一个层级、一个方向**。

禁止：

- 同时改 alpha 参数和主路由
- 同时改过滤器和止损
- 同时改权重映射和选股阈值

如果一次改动跨了多层，回测结果不可归因，等于浪费一次迭代。

### 4. 基本面主策略慎用硬门控

对基本面价值 / 红利质量 / 低频主仓类策略：

- `01 情绪开关`
- `11 一致性`
- `26 扩散指数`

默认只适合做**确认层 / 降档层 / 再进场层**，不适合直接做“全开/全关”总闸门。

优先使用：

- 总暴露缩放
- 现金缓冲
- 仓位降档
- 双确认后恢复

而不是频繁空仓。

## 分层定义

把增强动作分成 4 层：

### L0 工程与执行正确性层

解决“策略写法是否正确、状态是否接通、执行是否可信”。

典型内容：

- 状态变量写入 / 清理
- `entry_dates / avg_costs / hold_list / target_list` 一致性
- 买卖流程是否和策略意图一致
- 目标持仓去重
- 目标权重 / 现金缓冲 / 仓位总和
- 规则是否真正在运行，而不是名义存在

### L1 Alpha 参数层

解决“当前 alpha 选什么、选几只、阈值多严格”。

典型内容：

- 持仓数
- 估值区间
- 市值区间
- 质量阈值
- 成长阈值
- 股票池范围
- 排序规则微调

### L2 主路由与总暴露层

解决“市场是否允许做、总仓位做到几成”。

典型内容：

- `route_scale`
- 市场状态分档
- 现金比例
- 主路由阈值
- 调仓频率
- 风格切换是否应升级为真正的总暴露控制

### L3 过滤、确认、风控增强层

解决“是否允许升档 / 恢复 / 降档，以及单笔风险和执行摩擦”。

典型内容：

- 双确认
- 再进场状态机
- SignalMaker 投票
- 波动率缩放
- 移动止损 / 时间止损
- 单票上限
- 行业上限
- 涨停打开卖出

### 第 2 步：先做工程审计（必做）

#### 工程审计清单

- [ ] 是否存在声明了但没写入的状态变量？
- [ ] 是否存在写入了但从不清理的状态变量？
- [ ] 主路由是否真的影响**总暴露**，而不是只改风格权重？
- [ ] 时间止损 / 移动止损 / 再进场逻辑是否真正接通？
- [ ] 涨停打开卖出是否只作用于“应观察的持仓”，而不是全部持仓？
- [ ] 买入后是否记录了成本、入场日期、持仓状态？
- [ ] 卖出后是否同步清理成本、入场日期、状态缓存？
- [ ] 目标股票列表是否去重？
- [ ] 是否有显式现金缓冲？
- [ ] 是否有单票上限 / 行业上限 / 持仓上限？
- [ ] 是否存在永远不会触发的死代码？
- [ ] 是否存在“研究口径”和“实盘口径”混杂？

#### L0 优先规则

只要发现明确结构问题，下一轮必须优先修一个 L0 问题。

不要在存在明显结构漏洞时继续调 alpha 参数。

#### 重要说明

`run_iteration.py` 的最终 keep / rollback 仍由统一 scorer 决定。

也就是说：

- **最终系统决策**：仍然是全局 score 严格比较
- **分层验收**：用于你在 `search_notes.md` 中记录“这一层是否值得继续深挖”

不要把这两者混为一谈。

#### 分层验收规则

##### L0 工程与执行正确性

重点不是“多赚多少”，而是：

- 逻辑是否真正接通
- 状态是否一致
- 执行是否更接近实盘
- 是否减少明显失真

如果因为统一 scorer 导致 rollback，但该改动修复了明确结构问题：

- 不要把它简单记为“机制无效”
- 记录为“必要工程修复，需在 champion 上以更小改动重做”

##### L1 Alpha 参数层

重点看：

- 年化
- score
- MaxDD
- 最近 1-2 年是否恶化

只要明显削弱原始 alpha，就视为无效。

##### L2 主路由与总暴露层

重点看：

- 是否真正控制总暴露
- 是否减少大回撤
- 是否减少不必要的频繁切换
- 年化是否被过度拖累

如果主路由把策略频繁打成空仓，通常判为无效。

##### L3 过滤、确认、风控增强层

重点看：

- 是否改善恢复质量
- 是否减少噪声交易
- 是否降低单笔大亏
- 是否降低组合波动 / 换手

过滤器默认只能“修正、确认、延迟恢复”，不能取代主路由。

更新 `search_notes.md`：

- keep → 归入“已验证有效”，注明层级
- rollback → 归入“已验证无效”，注明为什么无效
- 工程修复但 rollback → 归入 “L0 工程候选”，不要误记成机制无效
- crash → 写清 crash 原因，并说明属于哪一层

**回到第 1 步，继续循环。**

## 简洁性原则

- score 提升 < 0.001 但增加大量代码 → discard
- 删掉代码后得分持平或更好 → keep（简化胜利）
- 机制代码超过 30 行且效果不明显 → 考虑简化实现
- 对 L0 工程修复，优先选择最小改动接通逻辑，而不是大重构

---

## 效果优先原则

- **优先尝试能解释的改动**：不是“可能有效”，而是“明确属于哪一层、解决什么问题”
- **参数微调优先于机制堆叠**：对主仓 alpha 原型，先把已有参数调顺
- **过滤器默认后置**：只有当 alpha 与主路由基本稳定后再加
- **硬门控慎用**：若一个过滤器显著降低交易频率但拖累年化过多，通常不适合主仓默认启用
- **工程缺口先补**：任何未接通规则，都优先于继续调参

## 评分公式

```text
calmar = annual_return / max(abs(max_drawdown), 0.01)
score = calmar * 0.55 + sortino * 0.25 + information_ratio * 0.20
```

统一 scorer 规则仍然是：

- 新 score **严格大于** champion score 才 keep
- `abs(max_drawdown) > 0.35` 直接 rollback

但你在搜索地图里的记录和后续方向选择，必须同时参考：

- 它属于哪一层
- 它解决了什么问题
- 它是“机制无效”还是“工程未接通”

不要把所有 rollback 都记成“这个机制没用”。
